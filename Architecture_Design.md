# Architecture Design — Smash Arena

## Что за проект

Сетевая 2D-арена в духе Super Smash Bros.: 2–4 игрока на плоской карте, удары друг друга, knockback растёт с накопленным уроном. Цель — выбить противника за пределы арены.

Документ фиксирует архитектуру, выбранную на этапе практики №1. Цель — чтобы любой член команды за пять минут понял, какие классы есть, кто что делает и почему приняты те или иные решения.

## Общая схема

```
        +-------------------+
        |  Authoritative   |
        |     Server        |
        |  (single source   |
        |    of truth)      |
        +---------+---------+
                  |
         UDP (unicast + broadcast)
                  |
   +--------------+--------------+--------------+
   |              |              |              |
+--+-----+    +---+----+    +----+---+     +----+---+
|Client 1|    |Client 2|    |Client 3|     |Client 4|
| ввод + |    | ввод + |    | ввод + |     | ввод + |
| рендер |    | рендер |    | рендер |     | рендер |
+--------+    +--------+    +--------+     +--------+
```

Сервер — единственный, кто знает «как устроен мир». Клиент только рисует то, что пришло, и шлёт ввод.

## Топология сети

**Выбор: Dedicated Server (выделенный авторитетный сервер)**

### Рассматривались три варианта

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Dedicated Server** | Один источник правды, простая отладка, легко фильтровать читеров (всё считается на сервере), стандарт индустрии | Нужен отдельный процесс/машина, которая живёт, пока идёт матч | ✅ Берём |
| **Listen Server** (один из клиентов = сервер) | Не нужен отдельный хост, легко запустить «поиграть вдвоём» | Хост имеет полный контроль над миром, можно тривиально читерить. Когда хост выходит — матч умирает | ❌ |
| **P2P** (все клиенты равны, общаются друг с другом) | Нет сервера, минимальные требования к инфраструктуре | Задержки по топологии O(N²), нужен консенсус о «правде» (кто первее нажал кнопку?), голосование за хоста при дисконнекте, NAT-траверс | ❌ |

**Вывод:** dedicated server. Это правильный выбор для любого соревновательного мультиплеера. Студенту проще отлаживать: лог в одном месте, нет «у меня работает, а у друга — нет».

## Физическая модель

**Выбор: 2D, вид сверху, плоская арена, без гравитации**

Smash Bros — это 3D, с платформами, прыжками, разными высотами. Для первой итерации всё это лишнее. Если оставить плоскую арену с видом сверху:

- Движение превращается в `x += dx * speed * dt`, `y += dy * speed * dt`. Никаких векторов вверх/вниз.
- Столкновения — простые AABB-прямоугольники (axis-aligned bounding box). Без учёта высоты.
- Knockback — просто вектор, который прибавляется к скорости, плюс затухание.

Суть Smash — damage% влияет на knockback — сохраняется. Платформы, прыжки, разные этажи — это геймплей, который добавляется позже, если будет время.

## Ответственности

### Сервер

- Принимает UDP-пакеты от всех клиентов.
- Парсит заголовок, по `type` определяет команду.
- Применяет команду к нужному `Player` через `World::applyCommand()`.
- Каждые 50 мс (20 Гц) формирует `WorldState` и рассылает его всем подключённым клиентам.
- Пишет лог всех входящих команд: `[timestamp] type=X seq=Y from client Z`.

### Клиент

- Раз в секунду (на старте) отправляет команду MOVEMENT, отправляет SHOOT по нажатию.
- Слушает сервер, получает `WorldState`, обновляет локальный список игроков.
- Рисует всех, включая себя. На текущем этапе «рисование» = вывод в консоль (X Y HP%). Графика подключается на следующих практиках.

### Player (только на сервере)

- Хранит id, позицию, скорость, hp, damagePercent, alive-флаг.
- Никакой логики «сам по себе» — изменения только через `World::applyCommand()`.

### World (только на сервере)

- Хранит арену (размеры) и список `Player`.
- `applyCommand(MovementCmd)` — обновляет позицию игрока.
- `applyCommand(ShootCmd)` — ищет попадание, наносит урон, считает knockback.
- `update(dt)` — двигает игроков по инерции, гасит скорость, проверяет вылет за арену.
- `serialize()` — собирает `WorldState` (id + pos + hp + damage + alive для каждого игрока).

### PacketHeader

- `type`: тип команды (`MOVEMENT=1`, `SHOOT=2`, `STATE=3`).
- `seq`: счётчик пакетов, для отладки и детекта дублей/потерь.
- `size`: размер полезной нагрузки, чтобы парсер знал, сколько байт читать дальше.
- Структура упакована через `#pragma pack(1)` — никакого выравнивания, иначе клиент и сервер на разных платформах не договорятся.

## Сценарий матча

1. **Подключение.** Клиент отправляет пакет `CONNECT` (в расширенной версии). В первой итерации клиент просто начинает слать MOVEMENT, сервер при первом пакете от нового адреса регистрирует игрока с минимальным свободным `id`.
2. **Основной цикл.** Клиент шлёт MOVEMENT (1 раз/сек) и SHOOT (по нажатию). Сервер обновляет `World`, рассылает `STATE` всем 20 раз/сек.
3. **Удар.** Сервер при обработке SHOOT смотрит, кто в радиусе атаки. Если попал — `victim.damagePercent += weaponDamage`, `victim.vx/vy += knockbackVector * (damagePercent * 0.02)`.
4. **Вылет.** Если игрок вышел за границы арены — `isAlive = false`, в логе `[DEATH] player N by knockback`.
5. **Respawn.** Возвращается в центр, hp восстанавливается, damagePercent обнуляется. (Запланировано на следующие практики.)

## Что НЕ входит в первую итерацию

Сознательно отложено, чтобы не раздувать скоуп:

- Графика и UI — следующая практика.
- Реальная физика (отскоки от стен, сложные хитбоксы).
- Меню выбора персонажа — пока один тип бойца.
- Авторизация (логин/пароль) — это доп. задание первой практики, добавим, если успеем.
- CRC32 — тоже доп. задание, отложено.
- Respawn — записан в планах, реализуется вместе с физикой.

## Открытые вопросы

- **Частота рассылки STATE.** Сейчас 20 Гц. Для 4 игроков с 8 байтами на каждого это 4 × 8 × 20 = 640 байт/сек на клиента. Можно поднять до 30 Гц без проблем.
- **Что делать с потерянным STATE-пакетом.** Пока — ничего, ждём следующего. Никакой интерполяции, никакого предсказания. Для 20 Гц лаг в 50 мс терпимый.
- **Когда клиент узнаёт свой `id`.** В первой итерации — привязка по адресу клиента. С авторизацией — при логине.
