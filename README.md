# Smash Arena

## 1. Проект, топология, архитектура

### Проект

**Smash Arena** — сетевая 2D-арена в духе Super Smash Bros. 2–4 игрока на плоской карте, удары, knockback растёт с накопленным уроном. Цель — выбить противника за пределы арены. Сквозной проект по дисциплине «Разработка многопользовательских игр и клиент-серверных систем».

### Топология

**Dedicated Server** — выделенный авторитетный сервер, с которым все клиенты общаются напрямую через UDP.

```
        +-------------------+
        |  Authoritative   |
        |     Server        |
        +---------+---------+
                  |
             UDP (unicast)
                  |
   +------+-------+-------+------+
   |      |       |       |      |
+--+--+ +--+--+ +--+--+ +--+--+
|Cl 1| |Cl 2| |Cl 3| |Cl 4|
+----+ +----+ +----+ +----+
```

### Архитектура

Сервер — единственный источник правды: хранит мир, считает движение, удары, knockback. Клиент — терминал: ловит ввод, отправляет команды, рисует то, что пришло от сервера.

| Компонент | Ответственность |
|---|---|
| **Server** | UDP-сокет, цикл приёма, разбор заголовка, лог всех команд, рассылка `STATE` 20 раз/сек |
| **World** (на сервере) | Список `Player`, размеры арены, обработка команд, расчёт столкновений и knockback |
| **Player** (на сервере) | id, позиция, скорость, hp, damage%, alive |
| **Client** | UDP-сокет, периодическая отправка `MOVEMENT`, `SHOOT` по нажатию, приём `STATE`, отрисовка |

Команды на текущей итерации: `MOVEMENT` (направление движения) и `SHOOT` (атака с направлением). Формат пакетов описан в `docs/Protocol_Specification.md`, детали архитектуры — в `docs/Architecture_Design.md`.

## 2. Обоснование топологии

Сравнивали три варианта. Решение принято по четырём критериям: число игроков, нагрузка, задержки, бюджет.

| Критерий | Dedicated Server | Listen Server | P2P |
|---|---|---|---|
| Число игроков | 2–32 (нам 2–4 ✓) | 2–8 | 2–8 |
| Нагрузка | Линейная O(N) | Линейная O(N), но у хоста +50% (рендер + логика) | Квадратичная O(N²) на обмен |
| Задержка | Один hop, предсказуемая | Зависит от хоста | Суммируется по топологии, нужен консенсус |
| Бюджет | Отдельный сервер (дешёвый VPS) | Бесплатно, но хост жертвует FPS | Бесплатно, но NAT-траверс добавляет сложность |

**Выбор: Dedicated Server.** Разберём по каждому критерию подробнее.

### Число игроков

Smash — камерный жанр, 2–4 бойца на арене, не MMO на 100 человек. На таких масштабах все три варианта технически работают, но Dedicated Server даёт запас для роста: если захотим добавить режим 4×4 или наблюдателей — сетка уже не ляжет. Listen и P2P упрутся в 8 игроков.

### Нагрузка

Прямой расчёт для нашего сценария (4 игрока, 20 Гц STATE-рассылка):

```
1 PlayerState  = 8 байт
4 игрока       = 32 байта
+ 1 байт count = 33 байта payload
+ 4 байта header = 37 байт / пакет
× 20 Гц        = 740 байт/сек на клиента
× 4 клиента    = 2.96 КБ/сек исходящего с сервера
```

Это **смехотворная нагрузка** — даже самый дешёвый VPS раздаст это тысячам матчей параллельно. UDP-заголовки добавляют ещё 8 байт на пакет, но и с ними речь про единицы килобайт в секунду, не про мегабиты.

Входящий трафик на сервер: клиент шлёт `MOVEMENT` (7 байт) раз в секунду и `SHOOT` (9 байт) по нажатию. В худшем случае 1 MOVEMENT + 1 SHOOT в секунду = 16 байт/сек × 4 = 64 байт/сек входящих. Вообще ничто.

P2P при 4 игроках даёт 6 пар соединений (4×3/2), каждое из которых дублирует STATE. Получаем 6 × 740 = 4.4 КБ/сек только на один матч по каждой линке — и каждое соединение видит свой кусок мира. Бессмысленное распыление трафика.

### Задержки

Экшен-игра требует, чтобы время от нажатия до визуального отклика было **< 100 мс**, иначе играть некомфортно. С Dedicated Server:

```
Ввод → клиент: 1 мс (локальная обработка)
Клиент → сервер: RTT/2 (типично 10–25 мс в интернете, <1 мс в LAN)
Сервер: 1 мс (применить команду)
Сервер → клиент: RTT/2
Отрисовка: 16 мс (один кадр при 60 FPS)
─────────────────
Итого: ~50–80 мс в интернете, ~20 мс в LAN ✓
```

Listen Server даёт те же цифры для хоста, но у остальных клиентов — `RTT/2 → хост` + `RTT/2 → хост` = двойной путь. При плохом соединении хоста страдают все.

P2P — в идеальном мире с прямой связью быстрее, но на практике это NAT-траверс, ретрансмиты UDP-hole-punching'а, и в итоге задержки нестабильные и непредсказуемые. Плюс десинхронизация: у каждого свой «правдивый» мир, нужна синхронизация с консенсусом — это и есть задержка.

### Бюджет

| Вариант | Серверные расходы | Клиентские требования | Сложность разработки |
|---|---|---|---|
| **Dedicated Server** | 1 VPS за ~$3–5/мес на десятки матчей, или свой ПК для LAN-тестов | Любой ПК, пинга только до сервера | Средняя. Один сетевой код, один игровой код |
| **Listen Server** | $0 | Хост должен тянуть игру + сеть, остальные — только игру | Простая на старте, потом кошмар с античитом и миграцией хоста |
| **P2P** | $0 | Все клиенты равны, нужны открытые порты или relay | Высокая. NAT-траверс, выбор координатора, разрешение конфликтов |

Учебный проект с бюджетом $0/мес прекрасно ложится на Dedicated Server в режиме «запустил на своём ноуте, играем по Wi-Fi». Для сдачи практики никаких затрат вообще не нужно. Если когда-нибудь захостим публично — Dedicated Server проще масштабировать, чем вылавливать баги P2P-синхронизации.

### Итог

**Dedicated Server** — единственный вариант, который одновременно:
- укладывается в наш масштаб (2–4 игрока) с запасом на рост,
- даёт нагрузку, которой можно пренебречь,
- обеспечивает стабильные задержки для экшена,
- не требует доп. затрат на инфраструктуру,
- упрощает разработку и отладку (лог в одном месте, одна реализация сетевого кода).

Listen Server хорош для прототипа «поиграть вдвоём за одним ПК», но смешивает роли. P2P — академически интересно, для продакшена дорого по сложности.

## Сборка и запуск

Код кроссплатформенный — собирается и под Linux, и под Windows.

**Linux / macOS:**
```bash
g++ server.cpp -o server
g++ client.cpp -o client
./server                 # в одном терминале
./client                 # в другом (по умолчанию 127.0.0.1:9000)
./client 192.168.1.42    # для игры по сети
```

**Windows (MinGW):**
```bash
g++ server.cpp -o server.exe -lws2_32
g++ client.cpp -o client.exe -lws2_32
server.exe
client.exe
client.exe 192.168.1.42
```

**Windows (MSVC):**
```bat
cl /EHsc server.cpp ws2_32.lib
cl /EHsc client.cpp ws2_32.lib
server.exe
client.exe
```

**Важно для Windows:** брандмауэр при первом запуске спросит, разрешить ли `server.exe` слушать порт — нужно разрешить (Private networks достаточно).
