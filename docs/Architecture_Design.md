# Architecture Design — сквозной проект (файтинг в духе Smash Bros / Brawlhalla)

## 1. Жанр и требования

Жанр: платформенный файтинг (2–4 игрока на арене, ближний и дальний бой,
подбираемые руны/оружие, выбывание при падении с арены). Ключевые требования
к сети:

- **Низкая задержка ввода.** Удар должен ощущаться мгновенным — задержка
  напрямую влияет на игровой опыт (в отличие от, например, стратегий).
- **Малое число игроков в сессии** (2–4), сессии короткие (несколько минут).
- **Честность/анти-чит важны умеренно** — это не киберспорт-шутер с призовыми,
  но подмена урона/позиции клиентом не должна быть тривиальной.
- **Бюджет студенческого/инди-проекта** — нет средств на постоянный парк
  выделенных серверов.

## 2. Выбор топологии

Рассмотренные варианты:

| Топология | Плюсы | Минусы |
|---|---|---|
| Dedicated Server | Полная авторитетность, честность | Затраты на хостинг, лишняя сложность для 2–4 игроков |
| Чистый P2P (mesh) | Нет затрат на сервер, минимальная задержка | Хост-читы, сложность синхронизации без общего авторитета |
| **Listen Server** (один из игроков хостит) | Не требует выделенного хостинга, простая NAT-модель (1 хост + подключения к нему) | Хост имеет небольшое преимущество по задержке; при отключении хоста рвётся сессия |

**Выбор: Listen Server с серверной авторитетностью.** Один из клиентов
одновременно выполняет роль сервера (как в текущей практической работе —
серверный процесс логически отделён от клиентского и может быть запущен на
машине хоста). Сервер остаётся источником истины по позициям/здоровью
(см. `server.cpp`: клэмпинг координат, проверка CRC32, отказ необработанным
командам без авторизации) — это защищает от простейших читов на клиенте, не
требуя затрат на выделенный хостинг. Для продакшена в будущем стоит
рассмотреть переход на выделенный сервер или готовый транспортный слой
([GameNetworkingSockets](https://github.com/ValveSoftware/GameNetworkingSockets),
[yojimbo](https://github.com/mas-bandwidth/yojimbo)) с поддержкой rollback
netcode — именно так устроена сеть в Brawlhalla-подобных играх, где важна
скрытая компенсация задержки при обмене ударами.

## 3. Основные классы и обязанности

```
┌─────────────────────┐        UDP         ┌──────────────────────┐
│   ClientRenderer      │ ───────────────▶ │      ServerManager      │
│  (ввод + отрисовка)  │ ◀─────────────── │ (авторитетная логика)  │
└─────────────────────┘   STATE_UPDATE     └──────────────────────┘
                                                     │
                                             владеет несколькими
                                                     ▼
                                              ┌─────────────┐
                                              │   Player     │  x N (2-4)
                                              └─────────────┘
                                                     │
                                              ┌─────────────┐
                                              │    World     │
                                              │  (Arena)     │
                                              └─────────────┘
```

- **Player** — состояние одного персонажа: позиция, скорость, здоровье,
  активные модификаторы от рун (см. `mechanics.md` п.5.1, действуют 15 сек),
  текущее оружие, состояние щита (кулдаун 5 сек, прочность). На сервере это
  единственный источник истины; на клиенте — локальная копия для отрисовки
  и интерполяции.
- **World / Arena** — центральная платформа + две боковые (выше центральной),
  таймеры спавна рун (каждые 10 сек) и оружия (каждые 15 сек, чередование
  ближний/дальний бой), проверка падения персонажа за пределы арены → смерть.
- **ServerManager** — авторитетный игровой цикл: принимает UDP-пакеты
  (`MOVEMENT`, `ATTACK_LIGHT/HEAVY`, `SHOOT`, `SHIELD`, `RUNE_PICKUP`,
  `WEAPON_PICKUP`), применяет их к соответствующему `Player`, валидирует
  (границы арены, кулдауны щита, авторизация), рассылает `STATE_UPDATE`.
  Ведёт лог всех полученных команд (текущая реализация — консольный лог
  с меткой времени и адресом отправителя).
- **ClientRenderer** — считывает ввод (ЛКМ/ПКМ — лёгкий/тяжёлый удар,
  WASD — движение, отдельная кнопка — щит), формирует и отправляет пакеты
  на сервер, получает `STATE_UPDATE`/`ACK` и обновляет визуальное
  представление. Не принимает решений об уроне/смерти самостоятельно —
  только показывает то, что подтвердил сервер.

## 4. Распределение обязанностей: сервер vs клиент

| Действие | Кто отвечает |
|---|---|
| Приём ввода игрока | Клиент |
| Отрисовка сцены, анимации, UI | Клиент |
| Финальное положение/здоровье персонажа | **Сервер** |
| Спавн рун/оружия по таймеру | **Сервер** |
| Проверка падения с арены → смерть | **Сервер** |
| Проверка получения смертельного урона | **Сервер** |
| Кулдаун щита, эффекты рун (15 сек) | **Сервер** |

Такое разделение сделано намеренно: сервер — единственный, кому доверяют
итоговое состояние игры, клиент — «глаза и руки» игрока. Это соответствует
модели, заложенной уже в тестовом UDP-обмене текущей практической работы
(`STATE_UPDATE` как ответ сервера на `MOVEMENT`).

## 5. Связь с механиками игры (mechanics.md)

Типы пакетов в `protocol.h` заведомо расширены под будущие механики, чтобы
протокол не пришлось переделывать:

- `MOVEMENT`, `SHOOT` — минимально обязательные по заданию.
- `ATTACK_LIGHT` / `ATTACK_HEAVY` — под ЛКМ/ПКМ из mechanics.md п.4
  (лёгкий удар — мгновенный, тяжёлый — с задержкой и большим отталкиванием).
- `SHIELD` — под механику блока (mechanics.md п.7, кулдаун 5 сек).
- `RUNE_PICKUP`, `WEAPON_PICKUP` — под спавн рун/оружия (mechanics.md пп.5–6).

Полная реализация боевой логики (урон, отталкивание, модификаторы от рун,
руна случайности и т.д.) выходит за рамки практической работы №1 и будет
добавляться поверх уже готового протокола на следующих этапах.
