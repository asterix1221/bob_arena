# Prediction_Implementation — Client-Side Prediction и Server Reconciliation (ПР №4)

В репозитории две реализации одной и той же схемы «клиент передаёт ввод — сервер решает — клиент предсказывает и
сверяется»:

- **Часть A — Godot 4** (`godot/`): сквозной проект bob_arena делается на Godot, поэтому это основная реализация.
  Запускалась и измерялась (36 тестов GDScript + сценарии T1–T6 по реальному ENet).
- **Часть B — Unreal Engine** (`Source/`, `BobArenaPrediction.uproject`): реализация по буквальному тексту задания
  (`CharacterMovementComponent`). В среде разработки не было движка, поэтому код не собирался и не запускался (см. часть B).

# Часть A — Godot 4

## A1. Общие сведения

| Поле | Значение |
|---|---|
| Проект | `godot/` (`BobArenaPrediction`), часть сквозного проекта bob_arena |
| Команда | **ЗАПОЛНИТЬ:** ФИО участников |
| Версия движка | Godot **4.7.2** stable (проверено на Linux headless; `config/features` в проекте — 4.4+) |
| Хеш коммита для демонстрации | **ЗАПОЛНИТЬ** перед сдачей: `git rev-parse --short HEAD` (ветка `feature/prediction`) |
| Эмуляция сети | встроенная `NetEmu` (`godot/scripts/net/net_emu.gd`): задержка в одну сторону + джиттер + потери на исходящем трафике клиента и сервера (RTT ≈ 2 × lag). Профили: `lag100` (100 мс, 0%), `lag175loss4` (175±25 мс, 4%) |

Почему не `tc netem`/Clumsy: нужен воспроизводимый прогон на любой ОС без прав администратора; формулы и логика от
способа эмуляции не зависят (так же сделано в ПР №2–3).

## A2. Поток данных

```
Клиент-владелец                                            Сервер (Listen Server, авторитет)
───────────────                                            ────────────────────────────────
 ввод (WASD, Shift) каждый физический тик (60 Гц)
   │ ClientPredictor.local_input
   ▼
 cmd = {seq, mx, my, dash}          ◄── ввод/намерение, позиции в команде НЕТ
   │ PlayerSim.step(state, cmd)  ── предсказание: рывок виден сразу
   │ pending += cmd; history[seq] = состояние после cmd
   │
   └── srv_cmds(последние ≤10 неподтверждённых) ──(NetEmu: lag/loss)──►  ServerSim.receive_cmds
                                                                          · отбрасывает дубликаты/старьё/лишние поля
                                                                          · очередь + «кредит» (≤6 команд за тик)
                                                                          ServerSim.tick → PlayerSim.step(cmd)
                                                                          · DashRules.validate → begin ИЛИ отказ
                                                                          · пропуск seq → «удержание» последнего ввода
   ◄── cli_owner {ack, state, rej, why} (30 Гц) ◄──────────────────────  owner_snapshot (аналог ClientAdjustPosition/Ack)
   │ ClientPredictor.on_owner_snapshot
   │   history[ack] совпал с серверным?  да → ничего
   │   нет → correction: state = серверное; повторить все pending-команды (reconciliation)
   │         визуальная ошибка гасится offset-ом (сглаживание), при >120 px — телепорт
   ▼
 клиент «догнал» сервер без разрыва соединения           world_snapshot ──► другие клиенты: RemoteInterp (интерполяция)
```

Вариант **без** предсказания отличается одним: `predict_dash=false` → в команду флаг `dash` не кладётся, клиент
шлёт отдельный reliable-RPC `srv_request_dash`, ничего не делает локально и видит рывок только в снимке сервера.

## A3. Роли компонентов

| Компонент проекта | Роль | Аналог в Unreal |
|---|---|---|
| `ServerSim` (`sim/server_sim.gd`) | Авторитет: принимает **недоверенные** команды, симулирует игроков, формирует снимки | `AGameMode` + серверная часть CMC |
| `main.gd` (Listen Server / клиент) | Тонкий «клей»: ENet, RPC, ввод, отрисовка, лог. Никакой игровой логики | `APlayerController` (сбор ввода и RPC) |
| `ClientPredictor` (`sim/client_predictor.gd`) | Предсказание, история, сверка, повтор команд, измерение отклика | `FSavedMove` + `ClientAdjustPosition` + `ClientUpdatePositionAfterServerUpdate` |
| `PlayerSim` (`sim/player_sim.gd`) | Детерминированный шаг: рывок, скорость, коллизии со стенами; общий для клиента и сервера | `UCharacterMovementComponent::PerformMovement` |
| `DashRules` (`sim/dash_rules.gd`) | Правила рывка: `validate` / `begin` / `tick_timers` (в тиках, не в секундах) | серверные проверки действия |
| `RemoteInterp` (`sim/remote_interp.gd`) | Отображение чужих игроков по снимкам + интерполяция | Simulated Proxy + network smoothing |
| `NetEmu`, `Bot` | Эмуляция сети; скриптованные сценарии T1–T6 | Network Emulation |

Авторитетность: сервер **никогда** не получает позицию. `receive_cmds` оставляет в очереди только `seq/mx/my/dash`
(лишние поля, например `pos`, отбрасываются), оси ввода квантуются и обрезаются `sanitize_move`, объём очереди и
«разгон» после лага ограничены (`MAX_QUEUE`, `CREDIT_CAP`) — клиент не может ни телепортироваться, ни ускорить время.

## A4. Действие — рывок и серверные проверки

Рывок (Shift): 11 тиков (≈0.18 с) на скорости 900 px/с в направлении ввода (без ввода — по последнему направлению);
ходьба 220 px/с. Кулдаун 72 тика (1.2 с), выносливость 100, цена 35, регенерация 25/с.

| Проверка (`DashRules.validate`, решает сервер) | Причина отказа | Смысл |
|---|---|---|
| рывок уже идёт | `already_dashing` | нет наложения рывков |
| остаток кулдауна == 0 | `cooldown` | ограничение частоты |
| выносливость ≥ цены | `no_stamina` | ограничение серией |
| направление и дистанция | — | считает сервер из квантованного ввода; клиент их не присылает |

Всё считается в **тиках фиксированного шага**, а не по часам: повтор команд на клиенте после коррекции даёт
побитово тот же результат, что серверная симуляция (это и проверяют тесты «reconciliation replays pending commands
(exact state)»). При отказе сервер пишет `[DASH] SERVER REJECTED ... reason=...` и сообщает владельцу причину в снимке
(`rej`, `why`) — клиент логирует `[DASH] REJECTED by server`.

## A5. Сравнение: без предсказания и с предсказанием (lag 100 мс в одну сторону, RTT ≈ 200 мс)

Числа из реального прогона (`docs/godot/runs/`, сводка — `docs/godot/runs/summary.md`):

| | Без предсказания (T2) | С предсказанием (T3) |
|---|---|---|
| Нажатие → рывок на экране клиента | **242 мс** (min = avg = max, n=3) — ждём ответ сервера | **0 мс** (рывок в ближайшем тике) |
| Нажатие → подтверждение сервером | то же 242 мс | 234 / 236 / 242 мс (min/avg/max, n=3) |
| Коррекции | 3 (макс. ошибка 22.7 px: клиент не знал о рывке и «догоняется») | 0 |
| Финальная ошибка клиент↔сервер | 0.000 px | 0.000 px |

Вывод: предсказание не ускоряет сервер (подтверждение приходит за те же ≈ RTT), но убирает ощущаемую задержку
управления; без предсказания клиента приходится «подтягивать» серверными коррекциями.

## A6. Расхождение и серверная коррекция (T5: lag 175±25 мс, 4% потерь, чит клиента)

Чит (только на клиенте): `F1` — игнорировать кулдаун/выносливость; `F2` — то же + рывок в 3 раза быстрее; `F3` — выкл.
В прогоне (`docs/godot/runs/T5_lag175loss4_cheat.client.log`, график `docs/media/correction_example.png`):

1. Клиент с читом «рывкует» до конца кулдауна → сервер: `SERVER REJECTED reason=cooldown` → клиент:
   `[DASH] REJECTED by server`, `[CORRECTION] #1 error=11.3 px, replayed 22 command(s)`.
2. С читом `x3` предсказанная дистанция в 3 раза больше серверной → коррекции #2–#6, максимальная ошибка 206.3 px
   (при ошибке > 120 px клиент телепортируется, меньше — сглаживается).
3. Чит выключен → клиент и сервер сходятся, **финальная ошибка 0.000 px**; соединение не рвётся, игра не зависает.

Рывок в стену без чита (T6) расхождения не даёт: у клиента и сервера одинаковые стены и один и тот же `PlayerSim`.

## A7. Ссылки, артефакты, ограничения

- Код: `godot/scripts/` (`sim/*` — логика, `net/net_emu.gd`, `main.gd`, `bot.gd`), тесты `godot/tests/run_tests.gd`
  (36 проверок: правила, детерминизм, защита от чужого ввода, потери/джиттер, чит, полный цикл на виртуальном времени).
- Логи прогонов: `docs/godot/runs/`; сводка и графики: `tools/godot_report.py` → `docs/media/*.png`.
- Матрица тестов: `docs/Prediction_Test_Matrix.md` (часть A заполнена фактическими числами).
- Запуск: `run_godot_demo.ps1`; автопрогон T1–T6: `tools/godot_scenarios.sh` (bash) или `run_godot_demo.ps1 -Role Scenarios`.

Известные ограничения:
- Это не `CharacterMovementComponent`: предсказание/сверка написаны вручную (идея та же, API Godot такого механизма
  из коробки не даёт). Задание буквально про Unreal — см. часть B.
- Эмуляция сети встроена в приложение (исходящий трафик), а не на уровне ОС; на localhost, а не между двумя машинами.
- Прогон автоматический (бот), в headless-режиме: видео экрана нет, вместо него — графики по логам.
- Unreliable-канал + избыточная отправка последних 10 команд вместо reliable: при потере >10 подряд команд сервер
  «удерживает» последний ввод (`gap_fills`), клиент потом исправляется коррекцией.

# Часть B — вариант на Unreal Engine (код написан, но НЕ компилировался и не запускался)

### 1. Общие сведения

| Поле | Значение |
|---|---|
| Проект | `BobArenaPrediction` (Unreal Engine, C++), часть сквозного проекта bob_arena |
| Команда | **ЗАПОЛНИТЬ:** ФИО участников |
| Версия Unreal Engine | **ЗАПОЛНИТЬ фактической версией** (в `.uproject` указано `5.8`; код написан на штатном API `CharacterMovementComponent`, не требующем других модулей) |
| Хеш коммита для демонстрации | **ЗАПОЛНИТЬ** перед сдачей: `git rev-parse --short HEAD` (ветка `feature/prediction`) |
| Применённые команды эмуляции сети | **ЗАПОЛНИТЬ** по факту прогона (рекомендуемые — в `Prediction_Test_Matrix.md`) |

> Проект «кодовый»: арена (пол, стены, свет) строится кодом из примитивов движка в `ABobGameState`,
> визуал персонажа — примитивы `/Engine/BasicShapes`, ввод привязан в C++. Поэтому в репозитории нет
> бинарных ассетов `Content/` — есть `Source/` и `Config/`. Архитектура повторяет шаблон Third Person
> (`ACharacter` + камера на `SpringArm`, шаблонные параметры перемещения).

### 2. Поток данных

```
Клиент-владелец (Autonomous Proxy)                       Сервер (Authority)
──────────────────────────────────                       ──────────────────
 нажатие Left Shift
   │ ABobCharacter::RequestDash
   ▼
 bWantsToDash = true            ◄── ввод/намерение, НЕ координаты
   │ TickComponent → ReplicateMoveToServer
   ▼
 SavedMove (FSavedMove_Bob):
   флаг, состояние рывка ДО хода
   │
   ▼
 UpdateCharacterStateBeforeMovement
   → Validate (земля/кулдаун/выносливость)
   → Begin: старт рывка СРАЗУ            ◄── локальное предсказание (CSP)
   │ PerformMovement (CalcVelocity = рывок)
   ▼
 SavedMoves.Add(ход)  ──ServerMove (compressed flags: FLAG_Custom_0, Accel, timestamp)──►
                                                           UpdateFromCompressedFlags → bWantsToDash
                                                           MoveAutonomous → PerformMovement
                                                           → Validate → Begin ИЛИ [DASH] REJECTED
                                                           ServerCheckClientError: позиции совпали?
                                         ◄── ClientAckGoodMove ── да (ход можно удалить из SavedMoves)
                                         ◄── ClientAdjustPosition ── нет: авторитетные Loc/Vel
   │ (при коррекции)                                       ◄── ClientDashRejected (если отказ): причина + состояние
   ▼
 ClientUpdatePositionAfterServerUpdate:
   позиция = серверная; для каждого неподтверждённого хода:
   PrepMoveFor (вернуть состояние рывка до хода) → MoveAutonomous → PostUpdate
   │
   ▼
 клиент «догнал» серверную реальность без разрыва соединения         AcceptedDashCount++ (реплицируется всем)
                                                                      │
 Simulated Proxy (другие клиенты): ReplicatedMovement + network smoothing ◄┘
```

Вариант **без** локального предсказания отличается одним: вместо `bWantsToDash = true` клиент вызывает
`ABobPlayerController::ServerRequestDashNoPrediction()` (Server RPC) и ничего не делает локально —
рывок начинается на сервере, а клиент видит его только через серверную коррекцию позиции и
реплицированный `AcceptedDashCount`.

### 3. Роли компонентов

| Компонент | Роль в проекте |
|---|---|
| `ABobGameMode` | Только сервер. Задаёт классы Pawn/Controller/HUD/GameState; создаёт две `APlayerStart` — стартовые позиции назначает сервер, а не клиент. |
| `ABobGameState` | Есть на всех машинах; в `BeginPlay` одинаково строит арену (коллизии клиента и сервера совпадают — иначе предсказание у препятствий расходилось бы). |
| `ABobPlayerController` | Владеет Pawn; Server RPC `ServerRequestDashNoPrediction` (дискретное действие без предсказания); консольные команды `BobCheatNoDashRules`, `BobCheatDashSpeed` для намеренного расхождения. |
| `ABobCharacter` | Ввод (WASD/мышь/пробел/Left Shift), камера, визуал; `RequestDash` (выбор пути: флаг или RPC); обратная связь сервера: реплицируемый `AcceptedDashCount` (+OnRep), `ClientDashRejected`; измерение отклика в логе/HUD. |
| `UBobMovementComponent` (наследник `UCharacterMovementComponent`) | Сетевая обработка движения и рывка: флаг в `compressed flags`, серверная валидация, детерминированная симуляция рывка, `FSavedMove_Bob` (сохранение и восстановление состояния), счётчик коррекций. |
| `BobDash::` (`DashRules.h`) | Чистые правила: `Validate`, `Begin`, `Tick` (используются и клиентом, и сервером; покрыты 15 юнит-тестами без движка). |
| `ABobHUD` | Диагностика на экране: режим, пинг, выносливость/кулдаун, число коррекций, отклик, последний отказ сервера. |

Перемещение (ходьба/прыжок/поворот) целиком на штатном механизме CMC: `SavedMoves → ServerMove →
ServerCheckClientError → ClientAdjustPosition → ClientUpdatePositionAfterServerUpdate`. Позиция клиента
серверу **не передаётся** и никогда не записывается в `ActorLocation` без проверки.

### 4. Действие «рывок» и серверные проверки

Рывок: клавиша **Left Shift**; на `DashDuration` (0.20 с) скорость становится `DashSpeed` (1800 uu/с) в
направлении ввода (без ввода — «вперёд»). Параметры — свойства `UBobMovementComponent`.

Что клиент отправляет: **только бит намерения** (`FLAG_Custom_0`) в составе обычного `ServerMove`, вместе с
ускорением и временной меткой хода. Направление и дистанцию сервер вычисляет сам.

Что проверяет сервер (`BobDash::Validate`, одинаково с клиентом, но решающее слово — за сервером):

| Проверка | Причина отказа | Смысл |
|---|---|---|
| персонаж на земле (`IsMovingOnGround`) | `not_grounded` | нет рывка в воздухе |
| рывок уже идёт | `already_dashing` | нет наложения рывков |
| остаток кулдауна ≤ допуска (0.03 с) | `cooldown` | ограничение частоты |
| выносливость ≥ цены (35 из 100, регенерация 20/с) | `no_stamina` | ограничение серией |
| направление/дистанция | — | вычисляются сервером из ускорения хода; клиент их не присылает |

Таймеры и выносливость продвигаются **только на `DeltaTime` хода**, а не по часам мира, поэтому
повторный проигрыш хода на клиенте после коррекции даёт тот же результат, что и сервер.
Допуск кулдауна 0.03 с сглаживает дрожание `dt` между клиентом и сервером (на обеих сторонах одинаков).

При отказе сервер пишет в лог `[DASH] SERVER REJECTED ...` и шлёт владельцу `ClientDashRejected` с причиной
и авторитетными значениями кулдауна/выносливости — клиент подтягивает свой счётчик (см. «Ограничения»).

### 5. Сравнение: без предсказания и с предсказанием

| | Без предсказания (`bob.PredictDash 0`) | С предсказанием (`bob.PredictDash 1`) |
|---|---|---|
| Что делает клиент по нажатию | отправляет Server RPC, ждёт | поднимает флаг, рывок виден в ближайшем кадре |
| Задержка «нажатие → реакция» | ≈ полный RTT + такт репликации (в логе `NO_PREDICTION ... response=`) | ≈ 1 кадр (`PREDICTION key->local response=`), подтверждение сервера — позже (`SERVER CONFIRMED`) |
| Как клиент приходит к серверному результату | серверная коррекция позиции (рывок «догоняет» клиента с задержкой) | коррекция не нужна, если локальный и серверный результаты совпали |
| Риск | ощущение «вязкого» управления | при расхождении — откат (rubber-band) |

Измерение: в логе (`Saved/Logs`, метки `[DASH]`) и в HUD («Last response»). Конкретные числа — в
`Prediction_Test_Matrix.md` (**заполняются после прогона**).

### 6. Расхождение и серверная коррекция

Намеренное расхождение — консольные команды клиента-владельца:

```
BobCheatNoDashRules 1     // клиент игнорирует кулдаун/выносливость (сервер — нет)
BobCheatDashSpeed 3       // клиент считает рывок в 3 раза быстрее (при включённом чите)
```

Сценарий: при активном чите игрок нажимает Left Shift до окончания кулдауна (или бежит рывком в стену).
1. Клиент предсказывает рывок (в чит-режиме считает его допустимым и/или быстрым).
2. Сервер получает флаг, но по своим данным кулдаун не истёк → `[DASH] SERVER REJECTED ... reason=cooldown`
   (или посчитал рывок короче) → позиции расходятся.
3. Сервер шлёт `ClientAdjustPosition` → клиент получает `[CORRECTION] #N ... error=... uu`, встаёт в
   серверную позицию и повторно проигрывает неподтверждённые ходы (`PrepMoveFor` возвращает состояние рывка).
4. Соединение не рвётся, игра не зависает, сервер не принимает недопустимое состояние.

Рывок «у препятствия» (стена в центре арены) расхождения без чита **не вызывает** — у сервера и клиента
одинаковые коллизии; это ожидаемо и тоже стоит показать.

Известные ограничения:
- Разработка шла без установленного Unreal Engine: код **не компилировался и не запускался** автором
  заготовки; проверена только чистая логика рывка (g++, ASan/UBSan). Запуск и сбор артефактов — на машине с UE.
- Состояние рывка (кулдаун/выносливость) в коррекцию CMC не входит. После отказа сервера клиент получает его
  отдельным `ClientDashRejected` (приблизительно, с запозданием на ~RTT/2 в консервативную сторону).
  Штатное решение — расширить `FCharacterMoveResponseData`; здесь выбран более простой путь.
- Ходы с рывком не объединяются (`CanCombineWith`), что чуть увеличивает трафик на время рывка.
- Читы действуют только на клиенте-владельце (`ROLE_AutonomousProxy`).
