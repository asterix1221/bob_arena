# Prediction_Implementation — Client-Side Prediction и Server Reconciliation в игре bob_arena (ПР №4)

Реализовано **в игре на Godot 4** (2D-платформер для 2–4 игроков на собственном UDP-протоколе из ПР №1–3), без Unreal Engine —
преподаватель разрешил любой движок. Схема везде одна: **клиент передаёт ввод, а не позицию; сервер сам считает и проверяет результат;
клиент предсказывает, сверяется с авторитетным состоянием и переигрывает неподтверждённые команды.**

## 1. Общие сведения

| Поле | Значение |
|---|---|
| Проект | bob_arena — многопользовательская игра на Godot 4, собственный UDP-протокол (ПР №1–3), Listen Server |
| Команда | Михеев Н.В., группа ИКБО-22-23 |
| Движок | Godot **4.7.2** stable (автотесты, сценарии и запись видео проверены на Linux; игра рассчитана на Windows 11 / PowerShell 7) |
| Коммит для демонстрации | код — `60487f7` (ветка `feature/game-prediction`; последующие коммиты меняют только документацию) |
| Раньше (первая версия ПР №4) | прототип на ENet — тег `pr4-submitted`; вариант на Unreal — ветка `feature/prediction-unreal` (не входит в PR) |

## 2. Поток данных

```
 клиент-владелец (GameClient)                              сервер (GameHost, Listen Server)
 ┌─────────────────────────────┐   Input {seq, axis, btn}   ┌─────────────────────────────────────┐
 │ 1. ввод → команда seq=N     │ ─────────────────────────▶ │ 4. очередь команд игрока            │
 │ 2. PlatSim.step() СРАЗУ     │   (по 2 тика, с избыточ-   │ 5. PlatSim.step() — ТОТ ЖЕ код      │
 │    (предсказание, history[N]│    ностью последних команд)│    + проверка рывка (кулдаун,       │
 │    pending += команда)      │                            │    выносливость, состояние)         │
 │ 3. показать результат       │ ◀───────────────────────── │ 6. снимок {ack=N', состояние}       │
 │                             │   Snapshot (60 Гц)         │    отклонённый рывок просто не      │
 │ 7. history[ack] == состоя-  │                            │    исполняется                      │
 │    ние сервера? да → ок     │                            └─────────────────────────────────────┘
 │    нет → КОРРЕКЦИЯ:         │
 │    state = сервер + повтор  │
 │    команд pending (seq>ack) │
 └─────────────────────────────┘
```

Файлы: `godot/scripts/game/game_client.gd` (шаги 1–3, 7), `game_host.gd` (4–6), `plat_sim.gd` (общий детерминированный шаг симуляции),
`pstate.gd` (состояние, побайтово сравнивается при сверке).

## 3. Роли компонентов (аналоги Unreal в этом проекте)

| Unreal | В bob_arena |
|---|---|
| GameMode (только сервер) | `GameHost`: матч, фазы, спавн, авторитетный шаг всех игроков, проверка команд |
| PlayerController | `App` + `InputLatch`: сбор ввода, фиксированный тик 120 Гц, отправка; при автопрогоне — `ScenarioBrain` вместо клавиатуры |
| Character | `PState` + `PlatSim` (одна и та же симуляция у клиента и сервера) |
| CharacterMovementComponent | `GameClient` (SavedMoves = `pending` + `history`, сверка `_reconcile`, повтор команд) и серверная обработка в `GameHost._consume`; снимок с `ack` играет роль `ClientAdjustPosition` / `ClientAckGoodMove` |
| Simulated Proxy | чужие игроки: интерполяция снимков (`remote_view.gd`), без предсказания |
| Network smoothing | `render_offset` — плавное «стекание» малой коррекции своего персонажа; ошибка > 120 px — мгновенный телепорт |

В Godot нет встроенного аналога CharacterMovementComponent, поэтому предсказание и сверка написаны вручную; отправка готовых координат
не используется нигде: в пакете только ось, кнопки и порядковый номер.

## 4. Выбранное действие — рывок (dash) и серверные проверки

Рывок: 22 тика (≈ 0.18 с) со скоростью 900 px/с, кулдаун 144 тика (1.2 с), стоимость 35 % выносливости. Клиент отправляет только бит
`BTN_DASH` и ось; направление и результат сервер вычисляет сам. Проверки (`PlatSim.dash_denied`, исполняются у сервера для каждой команды):

| Причина отказа | Условие |
|---|---|
| `already_dashing` | рывок уже идёт |
| `stunned` | персонаж оглушён |
| `attacking` | идёт анимация атаки |
| `cooldown` | таймер перезарядки > 0 |
| `no_stamina` | выносливость < стоимости рывка |

Дополнительно сервер санитизирует любой ввод: ось ограничена [-127; 127], кнопки маскируются, команды из «далёкого будущего»
(`seq > next_seq + 600`) отбрасываются (`bad_inputs`), дубликаты и опоздавшие игнорируются, пропущенные тики заполняются удержанием оси без
нажатий (разовые действия не «залипают»). Отказ сервера виден: `[DASH] SERVER REJECTED ... reason=cooldown` в логе хоста и «Рывок ОТКЛОНЁН
сервером» в игре.

## 5. Сравнение: без локального предсказания и с ним

Настройка «Предсказание рывка» (меню/пауза, клавиша **F4**, `--predict=0|1`): при выключенной клиент всё равно отправляет ввод, но рывок
на его экране появляется только после ответа сервера (ходьба и прыжок предсказываются в обоих режимах). Реальный UDP, два процесса, эмуляция
сети 100 мс в **одну** сторону на исходящем трафике каждой стороны (RTT ≈ 200 мс), 5 рывков на сценарий (`docs/game_runs/`, сводка — `summary.md`):

| | T2: без предсказания | T3: с предсказанием |
|---|---|---|
| Рывок на экране клиента после нажатия | **255–262 мс** (в среднем 258) | **0 мс** (в пределах тика) |
| Подтверждение сервера | то же (258) | 256–280 мс |
| Коррекций | 5 (по одной на рывок), ошибка до 136.5 px — персонаж «перескакивает» | 0 |
| Принято / отклонено сервером | 5 / 0 | 5 / 0 |

Графики: `docs/media/baseline_no_prediction.png`, `docs/media/prediction_enabled.png`. Видео: `baseline_no_prediction.mp4`, `prediction_enabled.mp4`
(в виртуальном времени: 283.3 мс против 0 мс — тот же эффект, значения детерминированы). В T3 подтверждение сервера приходит так же поздно,
как в T2, но игрок его не ждёт: его рывок уже идёт, а сервер лишь подтверждает его.

## 6. Расхождение и серверная коррекция (T5)

Клиентский **чит** (вручную: запуск с `--debug` (в лаунчере `-DebugKeys`), F10 — рывок без кулдауна, F9 — локальный телепорт на 300 px; в сценарии T5 включается скриптом): клиент локально игнорирует кулдаун и выносливость рывка
(`GameClient.cheat_no_rules`). Сеть: 175±25 мс, 4% потерь. Результат (3 прогона по реальному UDP, всегда одинаково по смыслу):

- сервер принял 5 рывков и **отклонил 3** (`reason=cooldown` в `docs/game_runs/T5.host.log`), клиент узнал об отказах (`dash_denied=3`);
- клиент получал коррекции (5–7 за сценарий; ошибка 50–150 px — это почти полный пролёт рывка, который сервер не исполнил);
- после коррекции клиент встаёт в серверное состояние и переигрывает неподтверждённые команды; итоговое расхождение с сервером — 0.000 px;
- соединение не рвётся, игра не замирает. Видео и скриншоты: `docs/media/correction_example.mp4`, `docs/media/shots/correction_example_*.png`.

## 7. Визуализация предсказания (настройки игры)

Меню и пауза: «Предсказание рывка» (вкл/выкл) и «Визуализация предсказания». Клавиши: **F4** — предсказание рывка, **F8** — режим по кругу.
Параметры запуска: `--predict=0|1`, `--viz=0..3`; `run_godot_demo.ps1 -Predict 0|1 -Viz 0..3`.

| Режим | Что видно |
|---|---|
| 0 — Выкл | как в обычной игре |
| 1 — Призрак сервера | рядом с вашим персонажем полупрозрачный оранжевый «призрак» — **последнее авторитетное положение** от сервера (отстаёт на ≈ RTT/2 + интервал снимков) |
| 2 — Предсказанный полупрозрачный | ваш (предсказанный клиентом) персонаж полупрозрачный, подтверждённое сервером положение — плотнее |
| 3 — Полная | оба + путь **ещё не подтверждённых команд** (точка на каждую), линия опережения, подпись `клиент (+N px, K команд)` |

Во всех режимах, кроме 0, при коррекции вспыхивает красное кольцо (≈ 0.7 с). В `net_graph` (F3) добавлены строки: предсказание рывка вкл/выкл,
отклик «на экране» и подтверждение сервера (последний/средний), число принятых и отклонённых рывков. Реализация: `view/pred_viz.gd` (только
отрисовка; «призрак» сервера повторяет форму спрайта персонажа), `GameClient.pending_path()`/`prediction_lead_px()` (данные, покрыты тестами), `PlayerDraw.draw(..., alpha)`.

## 8. Сети, сценарии и воспроизведение

Эмуляция сети — в приложении (на исходящих датаграммах каждой стороны; профили в настройках «Сеть»: нет / 100 мс / 175±25 мс и 4% потерь;
`--preset=0..2`). Сценарии T1–T5 (`--scenario=Tn --role=host|client`) запускают хост (Listen Server) и клиента, которым управляет
`ScenarioBrain` (бег по платформе, рывки в заданные моменты, чит в T5):

```powershell
.\run_godot_demo.ps1 -Role Scenarios                 # T1–T5, два процесса по UDP без окна, логи в docs\game_runs
.\run_godot_demo.ps1 -Role Scenario -Case T3 -Viz 3  # один сценарий с окнами — для записи экрана (OBS / Win+Alt+R)
python tools\game_report.py                          # сводка docs\game_runs\summary.md и графики docs\media\*.png
```

Видео и скриншоты в репозитории записаны **в режиме виртуального времени** (`--role=sim`, `tools/game_video.sh`): хост и клиент в одном процессе
(`GameHost`/`GameClient` поверх `LoopHub`), кадры синхронны с симуляцией. Логика та же, что по UDP, но результат не зависит от скорости
рендеринга — запись окна с настоящим UDP на слабой машине давала нестабильные результаты. Числа таблиц выше — из прогонов **по реальному UDP**.

- Ограничения: разброс результатов реального UDP зависит от загрузки машины (в одном из трёх прогонов в T3 была 1 коррекция с ошибкой 0 px из-за

  рывка клиент определяет по таймеру перезарядки в авторитетном состоянии (отдельного пакета «рывок отклонён» в протоколе нет — формат ПР №2–3 не менялся).
