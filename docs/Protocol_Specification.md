# Protocol Specification

Формат пакета: `[PacketHeader][Payload]`. Все структуры упакованы
(`#pragma pack(push, 1)`), выравнивание отключено — байтовый layout
одинаков на отправителе и получателе.

## Заголовок пакета — `PacketHeader` (9 байт)

| Поле | Тип | Смещение | Описание |
|---|---|---|---|
| `packetType` | `uint8_t` | 0 | Тип пакета, см. таблицу `PacketType` ниже |
| `sequenceNumber` | `uint16_t` | 1 | Порядковый номер пакета отправителя (для лога/будущего upordering) |
| `payloadSize` | `uint16_t` | 3 | Размер данных после заголовка, в байтах |
| `checksum` | `uint32_t` | 5 | CRC32 от payload (полином 0xEDB88320), проверка целостности |

## Типы пакетов — `PacketType`

| Значение | Имя | Направление | Payload |
|---|---|---|---|
| 1 | `MOVEMENT` | клиент → сервер | `MovementPayload` |
| 2 | `SHOOT` | клиент → сервер | `ShootPayload` |
| 3 | `ATTACK_LIGHT` | клиент → сервер | `AttackPayload` |
| 4 | `ATTACK_HEAVY` | клиент → сервер | `AttackPayload` |
| 5 | `SHIELD` | клиент → сервер | нет данных |
| 6 | `RUNE_PICKUP` | клиент → сервер | зарезервировано (не реализовано в пр.1) |
| 7 | `WEAPON_PICKUP` | клиент → сервер | зарезервировано (не реализовано в пр.1) |
| 8 | `STATE_UPDATE` | сервер → клиент | `StateUpdatePayload` |
| 9 | `ACK` | сервер → клиент | нет данных |
| 10 | `AUTH_REQUEST` | клиент → сервер | `AuthPayload` |
| 11 | `AUTH_RESPONSE` | сервер → клиент | `AuthResponsePayload` |

Пакеты 3–7 определены в протоколе на будущее (см. `Architecture_Design.md`,
раздел 5); в текущей практической работе реализована обработка только
`MOVEMENT`, `SHOOT`, `ATTACK_LIGHT/HEAVY` (базовый ACK), `AUTH_REQUEST`.

## Структуры payload

```cpp
struct MovementPayload {      // 12 байт
    float x;
    float y;
    float z;
};

struct ShootPayload {         // 1 байт
    uint8_t weaponId;
};

struct AttackPayload {        // 1 байт
    uint8_t attackType;       // 0 = light, 1 = heavy
};

struct AuthPayload {          // 64 байта
    char login[32];
    char password[32];
};

struct AuthResponsePayload {  // 1 байт
    uint8_t success;          // 1 — успех, 0 — отказ
};

struct StateUpdatePayload {   // 18 байт
    uint32_t playerId;
    float x, y, z;
    uint16_t health;
};
```

## Обработка ошибок на сервере

- Пакет короче `sizeof(PacketHeader)` — отбрасывается молча (защита от мусора).
- `payloadSize` в заголовке больше фактически принятых данных — отбрасывается,
  пишется в лог.
- CRC32 от полученного payload не совпадает с полем `checksum` — пакет
  считается повреждённым и отбрасывается, пишется в лог.
- `MOVEMENT` / `SHOOT` / `ATTACK_*` от неавторизованного клиента (не прошёл
  `AUTH_REQUEST`) — отклоняется, пишется в лог.
- Координаты в `MOVEMENT`, выходящие за границы арены
  (X: [-50, 50], Y: [0, 50], Z: [-50, 50]) — обрезаются сервером
  до границы, авторитетная позиция уходит клиенту в `STATE_UPDATE`.

## Пример обмена (движение)

```
Клиент → Сервер:  [MOVEMENT, seq=1, size=12, crc] { x=1.5, y=0, z=0 }
Сервер → Клиент:  [STATE_UPDATE, seq=1, size=18, crc] { playerId=1, x=1.5, y=0, z=0, health=100 }
```

## Авторизация (доп. задание)

Список допустимых пар логин/пароль зашит в `server.cpp` (для практической
работы — в продакшене должен браться из защищённого хранилища, не из
исходного кода):

```
player1 / pass1
player2 / pass2
```

Клиент обязан успешно пройти `AUTH_REQUEST` до отправки игровых команд —
иначе сервер их отклоняет (см. «Обработка ошибок»).

## Приложение: протокол телеметрии PING/PONG (ПР №2)

> **Актуализация (ПР №3):** описание ниже — формат версии 1 (заголовок 7 байт,
> только PING/PONG). С ПР №3 модуль `protocol/` работает с версией 2 —
> заголовок 8 байт (добавлено `requiresAck`), добавлены типы MOVEMENT, SHOOT
> и ACK; см. следующее приложение. Статусы ответов и формулы метрик не менялись.

Отдельный, НЕсовместимый с описанным выше протокол — своя пара
клиент/сервер (`client/ping_client.cpp` / `server/pong_server.cpp`),
свой порт по умолчанию (`27016` вместо `27015`), модули
`protocol/protocol.{h,cpp}`, `telemetry/telemetry.{h,cpp}`,
`telemetry/transport.{h,cpp}`. Причины изолировать, а не расширить
протокол выше, подробно разобраны в комментарии к
`protocol/protocol.h`; кратко: другой состав заголовка (нет `checksum`,
есть `protocolVersion`), другая (явная, не побайтовая) сериализация, и
явное указание задания рассматривать телеметрию как "изолированную
подсистему" до её интеграции с ACK/тайм-аутами/повторной передачей в ПР №3.

### Заголовок — 7 байт, сетевой порядок байт (big-endian)

| Поле | Тип | Смещение | Описание |
|---|---|---|---|
| `packetType` | `uint8_t` | 0 | `1` = PING, `2` = PONG |
| `sequenceNumber` | `uint16_t` | 1 | Идентификатор измерения |
| `payloadSize` | `uint16_t` | 3 | Размер payload в байтах (без заголовка) |
| `protocolVersion` | `uint16_t` | 5 | Версия формата (`kProtocolVersion = 1`) |

### PING — клиент → сервер, 15 байт всего

| Поле | Тип | Описание |
|---|---|---|
| `clientSendTimeUs` | `uint64_t` | Метка отправки по монотонным часам клиента (мкс) |

### PONG — сервер → клиент, 31 байт всего

| Поле | Тип | Описание |
|---|---|---|
| `clientSendTimeUs` | `uint64_t` | Эхо исходной метки клиента из PING (для RTT) |
| `serverReceiveTimeUs` | `uint64_t` | Метка приёма на сервере (только диагностика) |
| `serverSendTimeUs` | `uint64_t` | Метка отправки ответа сервером (только диагностика) |

Часы клиента и сервера НЕ синхронизированы: `RTT` считается исключительно
как `t_receive_client − t_send_client` по часам клиента; серверные метки
используются только чтобы прикинуть время обработки на сервере при
разборе логов, не участвуют в расчёте RTT/SRTT.

### Валидация на приёме (обе стороны, `telemetry::ReadHeader`/`ParsePing`/`ParsePong`)

- Датаграмма короче 7 байт (заголовок) — отбрасывается.
- `packetType` не входит в `{1, 2}` — отбрасывается.
- `protocolVersion` ≠ `kProtocolVersion` — отбрасывается.
- `payloadSize` из заголовка не совпадает с ожидаемым размером payload
  для данного `packetType` (8 для PING, 24 для PONG) — отбрасывается.
- Фактическая длина датаграммы ≠ `заголовок + payloadSize` (лишний "хвост"
  или недостача байт) — отбрасывается.

Ни один из этих случаев не приводит к падению процесса — сервер/клиент
пишут строку в лог и переходят к следующему пакету (см.
`server/pong_server.cpp`, `client/ping_client.cpp`).

### Статусы ответа (`telemetry::ResponseStatus`)

| Статус | CSV-значение | Когда присваивается |
|---|---|---|
| `Received` | `received` | PONG пришёл в пределах тайм-аута (1000 мс по умолчанию) |
| `Timeout` | `timeout` | PONG не пришёл за время тайм-аута |
| `LateResponse` | `late_response` | PONG пришёл, но позже тайм-аута |
| `DuplicateResponse` | `duplicate_response` | Повторный PONG на уже завершённое измерение |
| `UnknownResponse` | `unknown_response` | PONG с `sequenceNumber`, которого нет среди отправленных |

Подробности формул RTT/SRTT/джиттера/Loss Rate и результаты реального
эксперимента — см. `docs/Latency_Report.md` и `docs/Experiment_Config.md`.

## Приложение: надёжная доставка — ACK и `requiresAck` (ПР №3)

Расширение того же модуля `protocol/protocol.{h,cpp}`; формат версии 2
(`kProtocolVersion = 2`). Версия 1 (ПР №2) несовместима: заголовок стал на
байт длиннее, поэтому получатель версии 2 отбрасывает пакеты версии 1 (и
наоборот) на этапе `ReadHeader`. Серверы и клиенты ПР №2 нужно пересобрать.

### Заголовок — 8 байт, сетевой порядок байт (big-endian)

| Поле | Тип | Смещение | Описание |
|---|---|---|---|
| `packetType` | `uint8_t` | 0 | `1` PING, `2` PONG, `3` MOVEMENT, `4` SHOOT, `5` ACK |
| `sequenceNumber` | `uint16_t` | 1 | Номер пакета в потоке отправителя |
| `payloadSize` | `uint16_t` | 3 | Размер payload в байтах (без заголовка) |
| `protocolVersion` | `uint16_t` | 5 | Версия формата (`2`) |
| `requiresAck` | `uint8_t` | 7 | `1` — пакет требует подтверждения, `0` — нет |

Поле `requiresAck` добавлено в конец заголовка — смещения остальных полей
совпадают с версией 1.

### Типы пакетов

| Тип | Направление | Payload | Размер пакета | `requiresAck` |
|---|---|---|---|---|
| PING | клиент → сервер | `clientSendTimeUs` (8 байт) | 16 | всегда 0 |
| PONG | сервер → клиент | 3 × `uint64_t` (24 байта) | 32 | всегда 0 |
| MOVEMENT | клиент → сервер | `x`, `y` (`uint16_t` × 2) | 12 | 0 (ненадёжная команда) |
| SHOOT | клиент → сервер | `aimAngleDeg` (`uint16_t`), `weaponId` (`uint8_t`) | 11 | 1 (надёжная команда) |
| ACK | сервер → клиент | `acknowledgedSequence` (`uint16_t`) | 10 | всегда 0 |

Полезная нагрузка ACK — ровно структура из задания:

```cpp
struct AckPayload {
    std::uint16_t acknowledgedSequence;
};
```

Сервер отправляет ACK с тем же `sequenceNumber`, что у подтверждаемого пакета,
и тем же значением в `acknowledgedSequence`.

### Какие команды надёжные

- **SHOOT — надёжная** (`requiresAck = 1`): выстрел — дискретное событие,
  потеря которого меняет исход игры, а более «свежий» выстрел его не заменит.
- **MOVEMENT — ненадёжная** (`requiresAck = 0`): позиция отправляется часто,
  каждый следующий пакет делает предыдущий устаревшим; повторная отправка старой
  позиции только занимала бы канал и могла прийти позже новой.
- **PING/PONG** — не требуют подтверждений (ПР №2): потеря PING сама является
  измеряемым событием.
- **ACK** не требует подтверждения — иначе возникла бы бесконечная цепочка
  «ACK на ACK». Если ACK потерян, отправитель по тайм-ауту повторит исходный
  пакет, а получатель ответит новым ACK (эффект команды при этом применяется один раз).

Парсеры принимают `requiresAck` для SHOOT/MOVEMENT в обоих значениях (так
`SHOOT` можно сделать ненадёжным, а `MOVEMENT` — надёжным, если потребуется), но
отбрасывают PING/PONG/ACK с `requiresAck = 1`.

### Валидация на приёме (`ReadHeader` / `ParseXxx`)

Выполняется ДО чтения полей payload; любое нарушение — датаграмма отбрасывается
без падения процесса:

- длина датаграммы меньше 8 байт (заголовок);
- `packetType` вне `{1..5}`;
- `protocolVersion` ≠ 2;
- `requiresAck` вне `{0, 1}`;
- для PING/PONG/ACK — `requiresAck = 1`;
- `payloadSize` не равен ожидаемому для данного типа;
- фактическая длина датаграммы ≠ `8 + payloadSize`.

### Повторная отправка и дедупликация

Описание алгоритма (адаптивный RTO, ограничение числа попыток, окно
дедупликации на сервере) и результаты эксперимента — в
`docs/Reliability_Protocol.md`.

## Приложение: игровые пакеты для игры на Godot (этап «доработка игры», M1)

Заголовок (8 байт v2: `type u8 | seq u16 | payloadSize u16 | version u16 | requiresAck u8`) и версия формата
**не менялись**: бинарники и тесты ПР №2–3 остаются рабочими. Добавлены типы 6–12; `ReadHeader` принимает
`type ∈ [1, 12]`, первый неизвестный тип теперь 13 (одно существующее правило теста обновлено: «0 и 13», было «0 и 6»).
Все числа — big-endian. Версия игрового протокола (`kGameProtocolVersion = 1`) передаётся в `Hello`/`Welcome`.

| Тип | Код | Канал | Направление | Payload |
|---|---|---|---|---|
| Hello | 6 | надёжный (`requiresAck=1`) | клиент → хост | `gameProto u8, colorIdx u8, nameLen u8, name[≤16]` (UTF-8, непрозрачные байты) |
| Welcome | 7 | надёжный | хост → клиент | `status u8, gameProto u8, playerId u8, serverTick u16, tickRateHz u8, seed u32` (10 байт); `status`: 0 ок, 1 мест нет, 2 версия |
| Input | 8 | ненадёжный (`requiresAck=0`) | клиент → хост | `firstCmdSeq u16, count u8 (1..16), count × {axis i8, buttons u8}`; команда i имеет номер `firstCmdSeq+i` (mod 65536) |
| Snapshot | 9 | ненадёжный | хост → клиент | `tick u16, ackCmdSeq u16, nPlayers u8 (≤8), players, ownerLen u8 (≤96), ownerState, nRunes u8 (≤8), runes` |
| GameEvent | 10 | надёжный | хост → клиент | `eventId u16, kind u8, tick u16, a u8, b u8, x i16, y i16, v i16` (13 байт) |
| Leave | 11 | надёжный | любая | `reason u8` |
| Roster | 12 | надёжный | хост → клиенты | `count u8 (≤8), count × {id u8, color u8, flags u8 (бит0 хост, бит1 готов), nameLen u8, name[≤16]}` |

`PlayerEntry` (13 байт): `id u8, x i16, y i16, vx i16, vy i16, hp u8, flags u8, buffs u16`.
`RuneEntry` (6 байт): `id u8, type u8, x i16, y i16`. `ownerState` — непрозрачный блок полного состояния игрока-получателя
(нужен для сверки/reconciliation; формат задаёт симуляция). Кнопки `buttons`: прыжок 1, рывок 2, лёгкий удар 4,
тяжёлый 8, вниз 16, прыжок удерживается 32. В `Input` **нет позиций** — только ввод (требование ПР №4).

Строгие правила разбора (одинаковы в C++ и GDScript, проверяются golden-векторами):

- `Hello/Welcome/GameEvent/Leave` принимаются только с `requiresAck=1`; `Input/Snapshot` — только с `requiresAck=0`;
- `payloadSize` обязан совпадать с фактическим хвостом датаграммы, счётчики не выше лимитов, лишних байт нет;
- тип 0 и ≥12, чужая версия, `requiresAck>1` — отказ; разбор мусора никогда не падает (20 000 случайных датаграмм в тестах).

Семантика доставки (то же, что в ПР №3, `docs/Reliability_Protocol.md`): получатель надёжного пакета отвечает
`Ack` (в том числе на дубликат) и отбрасывает повторы окном `DedupWindow(1024)`; отправитель повторяет по адаптивному RTO
(без экспоненциального увеличения, как в ПР №3), после 6 попыток объявляет доставку проваленной. **Порядок надёжных
пакетов не гарантируется**, поэтому `GameEvent` идемпотентны: клиент игнорирует повторы по `eventId`.
Нумерация `seq` — общий счётчик на собеседника (16 бит, с переходом через 65535; тест проходит границу), у `Ack` в поле `seq`
стоит подтверждаемый номер. Keepalive: `Ping` 4 раза в секунду (тот же `Ping/Pong` ПР №2: на нём считаются RTT, джиттер и доля
потерянных пингов), молчание 3 секунды = обрыв (`peer_lost("timeout")`).

### Игровая семантика поверх пакетов (этап M2)

**Единицы и тики.** Симуляция целочисленная, 120 тиков/с: 1 px = 256 u, скорости в u/тик. Номера тиков и команд — 16 бит
с переходом через 65535 (≈ каждые 9 минут), развёртываются арифметикой `SeqUtil.unwrap16`.
Поля `PlayerEntry.x/y` — в 1/16 px (для отображения чужих игроков; точное состояние владельца — в `ownerState`).

**Фазы матча** (первый байт `ownerState`): 0 лобби, 1 отсчёт, 2 игра, 3 раунд завершён. Снимки не шлются в лобби.

**ownerState** = `phase u8` + блок состояния игрока (58 байт: `x,y,vx,vy i32; hp u8; биты alive/on_ground/jumping/facing/dash_dir u8;
coyote, jump_buf, drop_t, dash_left, dash_cd u8; stamina u32; atk_kind, atk_tick, atk_cd, hit_mask u8; stun u8; slow, invert u16;
11 × таймер руны u16`). Клиент сравнивает его побайтно с историей своего предсказания на момент `ackCmdSeq`.

**Сервер и ввод.** Команды буферизуются по номеру; исполняется по одной команде за тик на игрока (при накоплении >8 — по две).
Нет следующей команды, но есть более поздние (дыра) — восполняется «удержанием» без одноразовых нажатий (`gap_fills`); команд нет
совсем — ждёт 6 тиков, затем тоже заполняет, опоздавшая команда отбрасывается. Ось ограничивается −127..127, кнопки маской 0x3F,
команды дальше 600 номеров вперёд отбрасываются (нельзя «ускорить время»). Позиция от клиента не принимается в принципе.

**GameEvent.kind:** 1 ROUND_START; 2 HIT (a атакующий, b жертва, v урон, x/y px); 3 PICKUP (a игрок, b тип руны, v id руны);
4 DEATH (a погибший, b убийца или 255, v причина: 0 урон, 1 падение); 5 ROUND_END (a победитель или 255); 6 COUNTDOWN (v секунд);
7 JOINED; 8 LEFT; 9 STATS (a id, b убийства, v урон, x секунд жизни, y 1 если погиб); 10 LOBBY (возврат после матча).
Клиент игнорирует повторы по `eventId` (окно 512).

**Welcome.status:** 0 ок, 1 мест нет или матч уже идёт, 2 другая версия игрового протокола. Отказанному собеседнику хост даёт
2 секунды на доставку ответа и затем удаляет.
